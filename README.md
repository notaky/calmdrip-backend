## 1. サービス概要
レシピ・時間・スケールを同時に確認しながら抽出することに負担を感じるハンドドリップ初心者が、落ち着いて抽出を楽しめるようにするサービス。

レシピに合わせた抽出工程をタイマーと連動させ、必要なタイミングで音声や画面から案内することで、ユーザーがレシピ・タイマー・スケールを何度も確認する負担を減らす。

---

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

ハンドドリップ初心者のころ、美味しいコーヒーの淹れ方を再現しようとして、レシピ、スケール、経過時間の3つを同時に確認しながら抽出することに難しさを感じていた。
「次は何秒で、何gまで注ぐのか」を確認しながら、同時にスケールの数値も確認する必要があり、抽出そのものを楽しむ余裕がなくなっていた。
経過時間に応じて次の工程を案内してくれるツールがあれば、初心者でもレシピを再現しながら、より落ち着いて抽出を楽しめるのではないかと考えた。

---

### 2-2. なぜそれが「気になった」のか

自分が良いと思ったものを、他の人にも知ってもらうことが好きだから。
また、難しかったり面倒だったりする部分をツールで解消することで、初めて挑戦する人の迷いや戸惑いを減らし、本来の楽しさに集中できるようにしたいという思いがある。

---

## 3. 課題の整理（表面的になっていないか）

### 3-1. 表に見えている困りごと

ハンドドリップは、初心者にとって抽出手順を把握しながら実行することが難しい。
特にレシピを再現しようとすると、レシピ・経過時間・スケールの数値を同時に確認する必要がある。

---

### 3-2. 本当に解決したい課題は何か

「なぜそれが困るのか？」

#### なぜ？
レシピ、スケール、経過時間の3つを確認しながら、決められたタイミングで決められた量のお湯を注ぐ必要があるから。

#### なぜ？
レシピに沿って安定して抽出したい一方で、複数の情報を同時に確認することが抽出中の負担になるから。

#### なぜ？
レシピを再現することに頭がいっぱいで、抽出中の時間そのものを楽しむ余裕がなくなるから。


#### 本当に解決したい課題
レシピに沿った抽出を行うための負担を減らし、抽出中の時間そのものを楽しむ余裕を生み出したい。

### 4-1. 想定しているユーザー

#### 年齢

特定しない。

##### ①
ハンドドリップを始めたばかりで、抽出中に確認することが多く混乱してしまう人。<br>
アプリが、レシピの工程をタイマーと連動させ、必要なタイミングで音声・画面から案内することで、ユーザーがスケールの数値確認に集中できるようにする。

### 5-2. それでも自分が作りたい理由
既存サービスにも、レシピとタイマーを組み合わせて抽出を支援する機能が存在する。
そのため、単純に「レシピ付きタイマーを作る」のではなく、初心者が抽出中に感じる負担を減らすことに重きを置きたい。

#### 1. 抽出中の情報量
抽出中に多くの情報が表示されると、初心者にとっては必要な情報を探す負担になる可能性がある。<br>
そこで、何をすれば良いか直感的にわかるようにすることを優先する。

#### 2. 抽出開始時の操作
抽出開始と同時にタイマーが始まる設計では、準備が終わっていない場合に慌てる可能性がある。<br>
そのため、抽出開始 → 準備 → ステップ１の案内という流れにして、ユーザーが落ち着いて抽出を開始できるUIを設計する。

#### 3. レシピ登録時の計算
豆と湯の比率を入力する方式では、実際に使用したい量を直感的に指定しにくい場合がある。<br>
そのため、実際に使う豆と湯の量を直接入力する設計を検討する。

#### 4. レシピ登録時の操作性
工程の秒数や湯量の設定は、特定の数字を直接指定したい場面が多い。<br>
そのため、ボタンによる細かい調整ではなく、数値を直接入力できる設計を検討する。

## 7. このアプリで実現すること

### MVPで作る機能

- 匿名ユーザー
  - ユーザーごとに一意のトークンを発行し、Cookieに保存
  - 会員登録なしでレシピを保存できる
- レシピCRUD
- レシピコピー
  - アプリ内の既存レシピを自分のレシピとしてコピー
- 抽出補助タイマー
  - レシピの工程と経過時間を連動

MVPでは会員登録を後回しにし、「レシピを選択して、迷わず抽出を開始できる」という中心的な体験の検証を優先する。

### 本リリースで作る機能

- ユーザー登録 / 認証
- 抽出タイマー音声案内
- 抽出評価
- レシピ検索
- レシピお気に入り

継続利用やレシピ探索につながる機能を追加する。


## 8. このアプリの懸念点とその対策

### 懸念点: 初心者が継続して利用しない可能性

#### 何が問題になりそうか
初心者の使いやすさを重視しているが、初心者がサービスに慣れた後も継続して利用してくれるとは限らない。

#### なぜそう思うか
ユーザー自身が抽出に慣れたとき、アプリを利用する理由が弱くなる可能性がある。

#### そのために考えている対策
初心者向けのシンプルさを維持しながら、抽出が上達した後にも使える機能を段階的に追加する。

また、高度な機能を追加する場合でも、初心者が必要とする情報量を増やしすぎないように、設定でオン/オフの切り替えができる設計を検討する。

### 10-2. 技術選定の比較検討

#### バックエンド

##### 採用技術
Ruby on Rails

##### 検討技術
- Firebase
- Supabase

##### 採用理由
MVPだけ見ると、データ構造はシンプルでFireBaseやSupabaseなどのBaaSを利用する選択肢もあった。
しかし、フロントエンドとバックエンドを分離したWebアプリの開発を経験することを目的の一つとしているため、Railsを採用した。

#### フロントエンド
抽出タイマーを中心とした操作性の高いUIを作りたいためReactをベースに考えた。

##### 採用技術
Next.js

##### 検討技術
Vite + React

##### 採用理由
- レシピページをSNSで共有することを想定しているため、ページごとのタイトルや説明などのメタデータを設定したい。
- ユーザー体験を重視しているため、ページの性質に応じてレンダリング方式を選択することによる表示性能のメリットを得たい。
- ディレクトリ設計やルーティングに悩む時間を減らしたい。

### 今回チャレンジしたい点
- Rails API と Next.js の分離構成
- App Router を利用した開発<br>
  Pages Router を利用した経験があるため、今回は App Router を採用する。
  実際のアプリケーション開発を通して理解したい。
- 快適なUX設計<br>
  今回のアプリでは、機能数よりも抽出中の操作体験に重きを置く。

### 不安な点
- App Router での開発<br>
公式チュートリアル以外では開発が初めてのため少々不安がある。

- App Router での Rails API との通信<br>
Pages RouterでNext.jsからRails APIへ通信した経験はあるが、今回は App Router を利用するため、データ取得方法が違う点に不安がある。
